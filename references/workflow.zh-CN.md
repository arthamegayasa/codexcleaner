# CodexCleaner 工作流（中文）

## 目标

帮助用户把 Codex 左侧任务列表整理成一个清晰、可继续工作的集合，同时完整保护项目目录、代码和用户明确保留的任务。

## 三种处理方式

### 保留

保留项继续显示在活动任务列表中，适合正在推进、近期会继续、包含独特决策依据，或被用户明确指定保留的任务。

### 归档

归档是默认的收纳方式。归档会把任务日志移入 Codex 的归档存储；该任务从左侧活动列表消失，历史内容继续保留，并可通过取消归档恢复。

优先归档这些任务：

- 已完成且仍有参考价值；
- 暂时停止，未来可能继续；
- 包含需求背景、关键决策、排查过程或交接信息；
- 用户暂时无法确定是否还会使用。

归档的价值是同时获得整洁的活动列表和可恢复的历史记录。任务数量较多时，归档也能减少桌面端启动和列表渲染需要处理的活动数据。

### 永久删除

永久删除用于用户明确不再需要的任务。Codex 会删除持久化任务及其派生任务；该任务从左侧列表移除，历史内容不再可恢复。项目目录、Git 仓库、源代码和普通文件保持原样。

适合永久删除的任务：

- 明确废弃的实验、测试或空任务；
- 内容重复且已有更完整版本；
- 一次性排查已结束，结论已转移到文档或代码；
- 对应项目已经清理，任务本身也没有保留价值；
- 任务记录已损坏且底层会话文件已经不存在。

## 处理流程

### 1. 只读审计

优先使用宿主提供的任务列表与归档列表工具。需要检查 Windows 本地存储或侧栏异常时，在 Skill 根目录运行：

```powershell
python scripts/audit_codex.py
```

需要机器可读结果时运行：

```powershell
python scripts/audit_codex.py --json
```

审计脚本只读取任务元数据、父子关系、会话文件是否存在及文件大小；它不读取对话正文，也不修改数据库。

同时运行 `codex doctor --summary`，记录 Codex 版本和存储诊断结果。输出用于本地判断；分享报告前先检查其中的本机路径与任务标题。

### 2. 建议分类

按以下顺序判断：

1. 当前正在运行、置顶、用户点名保留或近期明确要继续的任务归入“保留”。
2. 已完成但仍可复用、可追溯或未来可能继续的任务归入“归档”。
3. 用户明确不再需要、重复、测试、空白或已经损坏且没有可恢复会话的任务归入“永久删除”。
4. 证据不足的任务归入“归档”或“待用户决定”，让历史记录保持可恢复。
5. 派生代理任务跟随其顶层任务处理；计划中列出顶层任务，并说明删除会包含派生任务。

建议表至少包含：动作、任务标题、任务 ID、会话大小、更新时间、判断理由、处理后的可见效果。分别汇总保留、归档、删除的任务数和已知空间大小。

### 3. 获取确认

归档前展示完整归档清单，并得到用户对该清单的确认。

永久删除前使用清晰、肯定的确认文本，例如：

```text
确认永久删除以下 N 个 Codex 任务及其会话数据；保留……；项目目录和代码保持原样；我知道删除后无法恢复。
```

确认覆盖当前列出的精确任务。清单发生变化时，展示更新后的清单并重新确认。归档与永久删除分开计数，确保用户清楚每一类动作。

### 4. 执行官方操作

在 Codex 桌面端工具可用时，优先使用任务归档、取消归档和删除工具。否则按 UUID 使用 CLI：

```powershell
codex archive <TASK_UUID>
codex unarchive <TASK_UUID>
codex delete <TASK_UUID> --force
```

`--force` 只用于用户已经明确确认的 UUID。逐项记录命令结果。某一项返回错误时，先验证实际结果，再决定后续动作，这可以准确识别“命令报错但文件已经移动或删除”的部分完成状态。

### 5. 验证结果

再次运行审计并核对：

- 每个保留任务仍处于活动状态且会话文件存在；
- 每个归档任务处于归档状态且可取消归档；
- 每个永久删除任务已从官方任务存储移除；
- 左侧活动列表只包含预期任务；
- SQLite 完整性检查返回 `ok`；
- 项目目录和代码保持原样。

向用户报告实际完成数、归档数、永久删除数、已释放空间和仍需处理的异常。

## 侧栏异常的判断

桌面端侧栏可能包含本地目录缓存。审计结果可按以下方式解释：

- `ghost_catalog_entries`：侧栏目录仍有条目，官方任务状态库已经没有该任务。该条目属于可清理的幽灵索引。
- `stale_archived_catalog_entries`：任务已经归档，活动侧栏目录仍保留旧条目。该条目属于可刷新或清理的归档索引。
- `state_rows_missing_rollout`：任务元数据仍存在，实际会话日志已经不存在。该任务无法正常恢复，需要先确认官方删除是否已部分完成。

出现“恢复对话失败”或 `no rollout found` 时，先完成上述判断。一个已经缺少会话日志的条目无法通过索引修复恢复正文；清理索引的作用是让左侧列表与真实存储状态重新一致。

## 数据库修复边界

数据库修复属于独立的维护动作，采用以下条件：

1. 官方归档或删除已经执行并完成复核；
2. 异常条目属于已归档的旧索引、官方状态库中不存在的幽灵索引，或会话文件已不存在的孤立元数据；
3. 用户单独确认清理这些精确 ID；
4. Codex 桌面端已完全退出；
5. 每个数据库先建立带时间戳的在线备份，并通过 `PRAGMA quick_check`；
6. 单个事务只删除已确认 ID 的关联元数据；
7. 修复后再次执行完整性检查并重启 Codex；
8. 备份保留到用户完成重启验证。

检测到未知表结构、活跃写入、数据库锁定或目标集合发生变化时，保持数据原状并向用户报告诊断结果。修复范围只包含 Codex 任务索引与孤立元数据。
